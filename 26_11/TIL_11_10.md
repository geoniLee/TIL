# TIL - 2026.11.10

## 오늘 진행한 내용

Create Potion의 저장·불러오기 UI와 자동 저장 흐름을 점검하고, 공통 UI 설정 관리 및 저장 슬롯 PR 상태를 검토했다. Unreal MCP를 통해 C++ 코드, 블루프린트 그래프, 위젯 트리를 확인했으며 **현재 반영된 구조**, **제공한 변경안**, **실행 검증이 필요한 항목**을 구분했다.

## 1. 컨테이너 공통 UI 설정 관리

인벤토리 및 포션 UI에서 사용하는 공통 치수와 색상의 관리 위치를 정리했다.

- `SlotSize`, `SlotPadding`, `DefaultSlotColor`를 `CPContainerSubsystem`에서 관리하는 방향을 확정했다.
- 현재 서브시스템에는 `SlotSize=75`, `SlotPadding=10`, `DefaultSlotColor=White`가 Config 없이 반영돼 있다.
- 포션 액체 색상은 기존 태그 DataTable의 `LiquidColor01`을 활용하고, 기본값은 `GetDefault`로 조회하는 구조를 검토했다.
- 위젯의 조회 코드 변경, 기존 include 및 두 `DeveloperSettings` 제거는 **아직 변경안 단계**이며 이번 조사에서 소스 수정이나 빌드는 수행하지 않았다.

**정리:** 공통 값은 하나의 관리 지점에서 유지하되, 데이터 테이블로 관리되는 개별 포션 색상과 기본 UI 색상을 구분한다.

## 3. 자동 저장 타이머와 Save/Load 역할 분리

### 타이머 생명주기 검토

`CPTimeSubsystem`이 `GameInstanceSubsystem`이며 `GameInstance.GetTimerManager`를 사용하는 점을 확인했다. UE 소스를 통해 같은 `GameInstance`에서 일반적인 맵 이동을 진행하는 동안 타이머를 유지할 수 있는 구조임을 조사했다.

- 자동 저장 간격은 **180초**로, 타이틀 복귀·게임 종료는 타이머 해제 시점으로 정했다.
- `CPSaveSubsystem`에 `StartAutoSave`, `StopAutoSave`, `Deinitialize` 구현이 반영된 상태를 확인했다.
- 로딩 중 저장 실행 차단은 별도 고려 사항이다. 현재 `AsyncLoadingScreen` 설정의 `bAllowEngineTick=false`인 블로킹 로딩에서는 로딩 중 TimerManager Tick이 진행되지 않는 구조를 확인했지만, 로딩 후 첫 프레임까지 포함한 동작을 실행 검증한 것은 아니다.
- 타이틀 새 게임, Book의 로드 성공, 타이틀 복귀 경로에서 시작·중지 호출 위치를 검토했다. 실제 타이머의 180초 주기 저장 성공은 아직 실행 검증하지 않았다.

### UI의 역할 분리

저장·불러오기를 하나의 모드 분기로 처리하는 대신, 사용 위치에 따라 역할을 구분했다.

| UI | 역할 |
| --- | --- |
| Common SaveLoad | `Slot1`, `Slot2` 수동 저장 및 `Slot0` 정보 표시 |
| Book SaveLoad | `Slot0`, `Slot1`, `Slot2` 불러오기 |
| QuickSlot (`Slot0`) | 자동 저장 전용. 수동 저장 및 삭제 기능 없음 |

현재 두 위젯의 `bIsSaveMode` 분기와 PauseMenu의 모드 설정은 제거돼 있으며, Common은 저장으로 바로 연결되고 Book은 로드 성공 후 `StartAutoSave(180)`을 호출하는 구성이 확인됐다. Book의 미사용 `ProcessSaveResult`, `SaveNotifText` 정리는 후속 변경 대상이다.

## 4. Slot0 UI와 확인창 표시 점검

### QuickSlot 표시 및 불러오기

MCP로 최신 위젯 트리와 그래프를 다시 확인한 결과 다음 연결이 반영돼 있었다.

- Common·Book 모두 `Slot0` 행이 `Visible`이며 파일 조회 후 레벨·시간을 표시하도록 연결돼 있다.
- Common의 `Btn_QuickSlot`은 비활성 상태로 유지한다.
- Book에서 `Slot0` 존재 여부를 확인한 뒤 불러오기 확인창을 열고 `LoadGame(0)`으로 연결한다.
- `Slot1`·`Slot2` 삭제 기능 및 공용 Confirm의 `OnClosed` 처리는 유지한다.

**발견한 문제:** 타이틀 Continue 버튼의 저장 파일 존재 조건이 `Slot1 OR Slot1 OR Slot2`로 연결돼 있다. 첫 번째 `DoesSaveGameExist`의 `SlotName`을 `Slot0`으로 바꿔야 **Slot0만 있는 경우에도 Continue가 활성화**된다. 이 수정과 플레이 검증은 수행하지 않았다.

### Confirm 문구 개선

저장·불러오기·삭제 확인창에서 조작 대상 슬롯을 명확히 보여주도록, 각 슬롯의 `TextBlock.GetText`로 화면에 표시 중인 이름을 가져와 다음 형식으로 출력하는 변경안을 검토했다.

```text
{SlotName}
{Message}
```

- `ToText(Object)`는 사용자에게 보이는 슬롯명이 아니라 위젯 객체 이름을 반환하는 문제를 발견했다.
- 후속 확인에서 Book의 로드·삭제 확인 경로에는 Text 프로퍼티를 읽는 방식으로 수정된 것이 확인됐다.
- 그러나 **Book 삭제 Confirm에는 여전히 불러오기 안내 문구**가 들어 있다. 삭제 여부를 묻는 문구로 교체해야 한다.
- 해당 수정과 실제 저장·불러오기·삭제 UI 실행 검증은 수행하지 않았다.

## 정리

오늘은 저장 시스템의 기능을 확대하는 작업뿐 아니라 **공통 데이터의 관리 책임**, **타이머 수명과 UI 호출 시점**, **Save/Load의 역할 분리**, **실제 위젯 그래프의 연결 오류**를 함께 점검했다.

특히 코드와 블루프린트의 연결이 존재한다고 해서 최종 동작이 보장되는 것은 아니므로, 확인된 구조와 실행 검증 결과를 분리해 기록할 필요가 있다. 다음 확인 대상은 **Slot0만 있는 경우 Continue 동작**, **삭제 Confirm 문구**, **자동 저장 및 타이틀 복귀 시 타이머 해제**, **저장 슬롯 변경 사항의 빌드·플레이 검증**이다.
