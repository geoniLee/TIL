# TIL - 2026.11.09

## 오늘 진행한 내용

Unreal Engine 5.8 프로젝트의 Save/Load UI를 점검했다. 저장 슬롯의 시간 표시 및 삭제 버튼 표시 조건을 분석하고, Confirm 팝업이 열렸을 때 뒤쪽 SaveLoad UI가 조작되는 문제의 원인을 추적했다. 

## 1. 저장 슬롯 UI 표시 로직 조사

### 플레이 시간 표시 단위 확인

- 현재 `UpdateSlot`은 `CPSaveGame.TotalWorldMinutes` 값을 60으로 나눈 몫과 나머지를 `{hour}:{Minute}` 형식으로 표시하고 있었다.
- 변수명과 달리 실제 값은 **초 단위**로 증가한다. `CPTimeSubsystem`이 1초마다 값을 1씩 증가시키며 Getter에서 별도 변환하지 않는 구조를 확인했다.
- 따라서 1시간 미만은 `분:초`, 1시간 이상은 `시간:분`으로 구분하는 표시 방안을 정리했다. 기존 두 자리 숫자 표시는 유지한다.
- **상태:** 표시 로직 변경안을 제시했으며, 실제 WBP 수정·실행 검증은 확인되지 않았다.

### 슬롯 삭제 버튼의 호버 조건

- 삭제 버튼을 저장 파일이 존재하면서 슬롯 행에 마우스를 올렸을 때만 노출하는 방향으로 검토했다.
- 후속 그래프 조사에서 `UpdateSlot`의 **저장 데이터 표시 조건**에도 호버 AND가 연결되어, 호버하지 않으면 저장 파일이 있어도 '저장 데이터 없음'으로 분기할 수 있는 문제를 확인했다.
- **데이터 존재 여부와 삭제 버튼 노출 조건을 분리**해야 한다는 점을 정리했다.
  - 슬롯 데이터 표시: `DoesSaveGameExist(Slot1/Slot2)` 결과 사용
  - 삭제 버튼 표시: 파일 존재 여부와 행 호버 상태를 함께 판단
- Common·Book 모두 삭제 버튼 가시성 관리를 `Event Tick`으로 옮기는 변경 방향을 검토했다. 후속 점검에서 Tick 연결은 확인됐으나, Common의 데이터 표시 Branch 조건은 미연결 `True`, Book은 호버 AND가 남아 있어 **전체 반영 완료로 판단할 수 없었다**.
- 행의 빈 공간에서 호버가 풀리는 문제는 `HorizontalBox`가 `SelfHitTestInvisible`이라 히트 테스트 대상이 되지 않는 구조와 연관된다. 행 자체를 `Visible`로 변경하는 해결 방향을 도출했다.
- **상태:** 관련 그래프에서 문제를 확인했지만, 표시·호버 동작의 최종 실행 검증은 수행하지 않았다.

## 2. Confirm 팝업 중 뒤쪽 UI 조작 문제 분석

### Common과 Book의 입력 경로 차이

- Common SaveLoad는 일반 뷰포트 팝업이고, Confirm은 더 높은 `ZOrder`로 표시된다. 전체 화면 `BackgroundBlur`가 히트 테스트를 받으면 뒤쪽 Common UI의 포인터 입력을 가릴 수 있다.
- 실제로 Common에서 Confirm 표시 중 뒤쪽 호버가 차단되는 것을 확인했다.
- 반면 Book SaveLoad는 `WidgetComponent`와 별도의 `WidgetInteractionComponent`를 통해 입력을 받는다. 따라서 **뷰포트의 Confirm 배경을 덮는 것만으로 Book의 가상 포인터 입력까지 차단되지는 않는다**. Book에서 뒤쪽 반응이 남는 현상도 확인했다.
- `UIManager.RegisterCreatedWidget`은 입력 모드 관리와 관계되지만, Book의 위젯 표시 계층을 바꾸거나 별도 `WidgetInteraction`을 중단시키지는 않는다.

### 입력 차단 방식 검토

처음에는 뒤쪽 위젯의 `SetIsEnabled(false)`를 검토했으나, Unreal의 기본 Disabled 그리기 효과로 UI가 흐려지는 문제가 있었다. 전역 `Slate.ApplyDisabledEffectOnWidgets` 변경이나 전용 Slate 래퍼도 조사했지만, 적용 범위와 구현 부담을 고려해 다른 방식을 선택했다.

최종적으로는 SaveLoad 위젯에 `bIsConfirmOpen` 상태를 두고, Confirm 표시 중 `HitTestInvisible`로 자식까지 히트 테스트에서 제외하며, 닫힌 후 기존 `SelfHitTestInvisible`로 복원하는 방향을 정리했다. 이 방식은 **외형을 유지하면서 입력만 제한**하는 목적이다.

### Confirm 종료 이벤트와 반영 상태

- 공통 Popup 클래스에는 `OnClosed` 델리게이트가 마련됐고, `RequestClose`에서 `UIManager.CloseWidget(this)` **이전**에 `OnClosed.Broadcast()`를 호출하는 순서가 현재 코드에 반영된 것을 확인했다.
- Common·Book SaveLoad 모두 두 Confirm 생성 경로에서 `OnClosed` 구독, `bIsConfirmOpen` 설정, `HitTestInvisible` 전환과 닫힘 콜백을 통한 복원 흐름이 블루프린트 그래프에 연결된 것을 확인했다.
- 삭제 버튼의 호버 조건에도 `NOT bIsConfirmOpen`을 반영했다.
- 다만 **Create Event에서 실제 선택된 함수명은 MCP로 확인하지 못했다.** Common에는 실행선이 끊긴 이전 `SetIsEnabled` 관련 노드가 남아 있으며, 실제 확인·취소·ESC 종료와 입력 차단·복원 동작에 대한 실행 테스트도 진행되지 않았다.

## 3. 정리 및 후속 확인

이번 작업에서 확인한 핵심은 **UI가 같은 화면에 표시되더라도 실제 입력이 전달되는 경로는 다를 수 있다**는 점이다. Common은 뷰포트 히트 테스트, Book은 별도 `WidgetInteractionComponent`를 사용하므로 모달 처리 방법을 구분해야 한다.

또한 저장 슬롯의 **데이터 존재 여부 판단**과 **삭제 버튼 표시 여부 판단**을 같은 조건으로 묶으면, UI 연출 조건이 실제 데이터 표시를 잘못 제어할 수 있다. 두 책임을 분리하는 것이 중요하다.

후속으로는 슬롯 표시 Branch와 행 호버 설정을 최종 점검하고, Confirm의 `OnClosed` 바인딩 함수 및 확인·취소·ESC별 동작을 실제 실행 환경에서 검증해야 한다. 오늘 확인한 그래프 연결만으로 모든 입력 문제가 해결됐다고 단정하지 않는다.
