# TIL - 2026.11.05

## 오늘 진행한 내용

Save/Load 데이터 일부가 복원되지 않는 현상의 원인을 추적하고, 진단 로그를 통해 실제 저장·복원 흐름을 검증했다. 또한 Common SaveLoad UI의 패딩 동작을 분석하고, 슬롯 정보 표시와 확인창·삭제 기능의 개선 방향을 정리했다.

## 1. Save/Load 복원 누락 원인 조사 및 로그 검증

### 변경 이력과 호출 경로 확인

다른 팀원 환경에서 **레벨은 복원되지만 인벤토리·도감·플레이어 위치가 복원되지 않는 현상**을 조사했다.

- 현재 작업 브랜치의 커밋과 과거 기준 버전을 비교해 저장 관련 변경을 추적했다.
- `e9938198`에서 고정 `Slot1` 호출을 `SlotIndex` 기반 `Slot0`~`Slot2` 구조로 바꾸고 `SaveGame`의 반환형을 `bool`로 변경한 것을 확인했다.
- 이후 `139f53b4`에는 SaveLoad 위젯 및 메뉴 연결 변경이 포함되었지만, **문제는 슬롯 선택 UI 작업 이전에 발생했다**는 정보를 바탕으로 이를 최초 원인에서 제외했다.
- 발생 시점의 `main(c0994fd8)` 그래프에서 `PauseMenu → SaveGame(1)` 및 `BookMenu Continue → SaveSubsystem.LoadGame(1)` 연결을 확인했다. 슬롯 인자 불일치나 서브시스템을 우회하는 로드 경로는 발견되지 않았다.
- 인벤토리·도감 수집/복원 함수, 위치 복원 처리, 저장 데이터 구조의 직접적인 변경도 확인되지 않았다.

따라서 단순히 슬롯 인자가 추가되었다는 이유만으로 세 데이터가 선택적으로 누락된다고 단정할 수 없었다. `ResetGameSession`의 실행 시점과 실제 로드 경로는 추가 검증 대상으로 남겼다.

### 진단 로그 추가 및 실행 결과

원인을 구분하기 위해 `CPSaveSubsystem.cpp`와 `CPContainerSubsystem.cpp`에 **진단 로그 52개**를 적용했다.

- 데이터 수집 → 파일 쓰기/읽기 → 서브시스템 전달 → 복원 대기 → 실제 적용의 단계별 상태 기록
- 인벤토리·도감 개수, 플레이어 좌표, 세션 초기화 호출 등을 추적
- 기존 저장/복원 순서 및 반환 동작은 유지하고 로그만 추가
- `git diff --check` 통과, **UE 5.8.1 `CreatePotionEditor Win64 Development` 컴파일 및 링크 성공**

실행 로그에서도 정상적으로 처리되는 사례를 확인했다.

- **PIE Slot1:** 인벤토리 3항목 대입 및 저장된 플레이어 위치 적용 확인
- **Standalone Slot2:** 로드 → 저장 → 재로드 과정에서 인벤토리 3항목, 도감의 채집물 3개·태그 3개, 월드 시간 103분, 플레이어 위치·회전 값의 일치 확인
- 재로드와 실제 복원 사이에 `ResetGameSession`이 실행된 흔적은 없었고, 해당 로그 구간에서 Save/Load 실패나 누락도 발견되지 않았다.

다만 **문제가 발생한 팀원의 저장 파일로 재현한 것은 아니다.** 로그상의 데이터 개수와 적용 직후 좌표가 일치해도 개별 아이템 참조의 유효성, 도감 UI 표시, 복원 이후 상태 유지까지 보장하는 것은 아니므로 원인은 확정하지 않았다. 비교한 브랜치 사이에는 진단 로그 외 기능 로직 차이가 없음을 확인했다.

## 2. Common SaveLoad UI 패딩 동작 분석

SaveLoad 위젯에서 `Slot1SizeBox`의 **Top Padding을 늘렸는데 오히려 Slot2와의 간격이 줄어드는 현상**을 분석했다.

- `Border`는 고정 크기 `700×800`, 내부 좌우 패딩은 40, 상하 패딩은 80으로 설정돼 있었다.
- 슬롯 `SizeBox`는 `500×100`으로 고정되고, 두 슬롯 모두 세로 정렬이 `VAlign_Center`였다.
- UI Manager, C++ 부모 클래스 및 확인한 위젯 그래프에는 패딩 값을 다시 설정하는 로직이 없었다.

UE 5.8의 Slate 배치 코드(`AlignChild`, `ArrangeChildrenInStack`)를 살펴보면 중앙 정렬에서 콘텐츠의 위치는 다음 관계를 따른다.

```text
중앙 정렬 오프셋 = (할당 높이 - 자식 높이) / 2 + Top - Bottom
Auto 슬롯 높이 = 자식 높이 + Top + Bottom
```

이 구조에서는 Slot1의 Top Padding을 20 늘렸을 때 Slot1 콘텐츠는 30, 다음 Slot2는 20 내려가 **두 버튼 사이 간격이 10 줄어든다**. 현재 조건에서 Top Padding을 0 / 20 / 40으로 변경했을 때 계산상 간격은 25 / 15 / 5가 된다.

따라서 단순히 `Auto` 슬롯이기 때문에 간격이 유지된다는 설명은 맞지 않았다. **두 `SizeBox`의 Vertical Box Slot 정렬을 `Top`으로 바꾸면 간격을 더 예측 가능하게 관리할 수 있다.** 이는 엔진 소스와 레이아웃 계산을 통한 분석 결과이며, 화면에서 변경 전후를 직접 비교하거나 위젯을 수정하지는 않았다.

## 3. 슬롯 표시 및 확인창·삭제 기능 개선 방향

### 슬롯 정보 표시

기존 슬롯명 중심 UI를 **첫 줄 슬롯명 / 둘째 줄 레벨명(왼쪽)·플레이 시간(오른쪽)** 구조로 바꾸는 변경안을 정리했다.

- 각 정보는 별도 `TextBlock`으로 관리하고, 버튼 내부에 `VerticalBox`와 `HorizontalBox`를 배치한다.
- `CPSaveGame`의 `LevelName`, `TotalWorldMinutes`를 사용해 저장된 레벨과 시간을 표시한다.
- 시간은 `시간 = 총 분 / 60`, `분 = 총 분 % 60`으로 계산한다.
- `ToText(Integer64)`에서 최소 정수 자릿수 2, 숫자 그룹화 비활성화를 적용하면 `152분 → 02:32`, `5분 → 00:05`처럼 표기할 수 있다.
- 표시용 레벨명은 `MakingLevel → 공방`, `MyLevel → 공방 앞`, `VillageLevel → 뮤타빌`, `NewFieldLevel → 협곡`으로 대응하는 안을 작성했다. 매칭되지 않는 레벨은 기존 이름을 유지한다.

이 변경은 **화면 표시만 대상으로 하며**, 저장 파일의 `LevelName`이나 실제 `OpenLevel` 입력값은 변경하지 않는다. 표시명 중 `MyLevel`의 구역 대응은 맵 구성에 근거한 추론이므로 적용 전에 확인이 필요하다.

### 공통 확인창과 슬롯 삭제

현재 저장·불러오기 흐름에서 **덮어쓰기에만 사용하던 Confirm 위젯**을 저장·불러오기·덮어쓰기·삭제에 공통으로 활용하는 방향을 검토했다.

- Confirm은 메시지 및 확인·취소 입력만 담당하고, 실제 작업은 부모 SaveLoad 위젯에서 수행한다.
- 슬롯 삭제는 `UGameplayStatics::DeleteGameInSlot`의 반환값으로 성공 여부를 확인하고, 성공 시 `UpdateSlot`을 호출하는 구조를 제안했다.
- 삭제 버튼은 슬롯 버튼 안에 중첩하지 않고 옆에 별도로 배치하며, `DoesSaveGameExist` 결과를 통해 활성 상태를 갱신하도록 설계했다.
- Book Menu는 페이지 인스턴스를 재사용하므로 슬롯 삭제 후 **Title의 Continue 버튼 활성 상태**도 다시 갱신해야 한다는 점을 확인했다.

현재 확인창은 고정 문구를 사용하고 있었으며, Save/Load 위젯의 해당 변경안과 삭제 기능은 **아직 직접 적용하거나 실행 검증하지 않았다.** Quick Slot의 이번 변경 포함 여부와 빈 슬롯 삭제 버튼 처리 정책도 별도 확인이 필요하다.

## 정리

오늘은 Save/Load 복원 누락 문제를 코드 변경 이력과 실제 실행 로그로 좁혀 조사했고, **현재 테스트 환경에서 저장·재로드 시 주요 데이터가 정상 복원되는 사례**를 확인했다. 다만 팀원 환경의 원인은 재현되지 않아 확정하지 않았다.

UI에서는 패딩 문제의 원인을 Slate의 **중앙 정렬 계산 방식**에서 찾았으며, 슬롯 정보 표시와 공통 확인창·삭제 기능은 구현 전 변경안으로 정리했다. 이후에는 문제 환경 재현과 UI 변경 적용 후 실제 저장·불러오기 테스트가 필요하다.
