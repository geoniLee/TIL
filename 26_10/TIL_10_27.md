# TIL - 2026.10.27

## 오늘 학습한 내용

**Chain of Responsibility(책임 연쇄) 패턴**의 개념과 C++ 구현 구조를 조사했다. 여러 객체가 하나의 요청을 처리할 수 있는 상황에서, 요청을 보낸 쪽이 처리 대상을 직접 선택하지 않도록 설계하는 방법을 살펴봤다.

## 1. Chain of Responsibility 패턴

책임 연쇄 패턴은 요청을 처리할 수 있는 객체(Handler)를 연결하고, **현재 Handler가 처리하지 못한 요청을 다음 Handler로 전달하는 행동 디자인 패턴**이다.

요청을 받은 Handler는 직접 처리할지, 다음 Handler에 넘길지를 판단한다. 일반적인 방식에서는 처리 가능한 Handler를 찾으면 연쇄를 종료한다. 필요에 따라 여러 Handler가 차례로 검사하고 특정 조건에서 처리를 중단하는 형태로도 구성할 수 있다.

```text
요청 → Handler A → Handler B → Handler C
          │             │             │
       처리 불가      처리 불가       요청 처리
```

## 2. C++ 구현 구조

NPC 상호작용 요청을 **퀘스트 → 상점 → 일반 대화** 순서로 처리하는 가상 예시를 구성했다. 아래 코드는 패턴을 설명하기 위한 일반 C++ 예제이며 실제 프로젝트에 적용한 코드는 아니다.

```cpp
#include <iostream>

struct FInteractionContext {
    bool bHasQuest;
    bool bCanTrade;
};

class FInteractionHandler {
public:
    virtual ~FInteractionHandler() = default;

    FInteractionHandler* SetNext(FInteractionHandler* InNext) {
        Next = InNext;
        return InNext;
    }

    virtual bool Handle(const FInteractionContext& Context) {
        return Next ? Next->Handle(Context) : false;
    }

private:
    FInteractionHandler* Next = nullptr; // 소유권 없음
};

class FQuestHandler : public FInteractionHandler {
public:
    bool Handle(const FInteractionContext& Context) override {
        if (Context.bHasQuest) {
            std::cout << "Quest\n";
            return true;
        }
        return FInteractionHandler::Handle(Context);
    }
};

class FShopHandler : public FInteractionHandler {
public:
    bool Handle(const FInteractionContext& Context) override {
        if (Context.bCanTrade) {
            std::cout << "Shop\n";
            return true;
        }
        return FInteractionHandler::Handle(Context);
    }
};

class FDialogueHandler : public FInteractionHandler {
public:
    bool Handle(const FInteractionContext&) override {
        std::cout << "Dialogue\n";
        return true;
    }
};

int main() {
    FQuestHandler Quest;
    FShopHandler Shop;
    FDialogueHandler Dialogue;

    Quest.SetNext(&Shop)->SetNext(&Dialogue);

    Quest.Handle({true, true});   // Quest: 앞선 Handler가 우선 처리
    Quest.Handle({false, true});  // Shop
    Quest.Handle({false, false}); // Dialogue
}
```

클라이언트는 첫 Handler에 요청만 전달한다. 이후 어떤 Handler가 처리할지는 각 객체가 판단한다. `SetNext()`의 포인터는 다음 Handler를 **소유하지 않으므로**, 연결된 객체의 수명을 별도로 관리해야 한다.

## 3. 게임 개발에서의 활용 가능성

- **NPC 상호작용:** 퀘스트, 상점, 일반 대화처럼 여러 동작이 가능한 NPC의 처리 우선순위 설정
- **입력 처리:** UI가 입력을 우선 처리하고, 처리하지 않은 입력만 게임플레이 로직으로 전달하는 구조
- **조건 검사:** 기능 실행 전 여러 조건을 순서대로 검사하고, 실패 시 이후 처리를 중단하는 구조

## 4. 장점과 주의사항

- **장점:** 요청을 보내는 코드와 실제 처리하는 코드를 분리할 수 있고, Handler의 추가·순서 변경이 비교적 쉽다.
- **주의사항:** 어떤 Handler가 요청을 처리하는지 추적하기 어려울 수 있다. 연쇄 끝까지 처리되지 않는 요청에 대한 대응도 필요하다.
- **적용 판단:** 처리 대상이나 우선순위가 바뀔 가능성이 크면 유용하지만, 처리 방식이 단순하고 고정되어 있다면 조건문이나 직접 호출이 더 명확할 수 있다.

## 정리

책임 연쇄 패턴의 핵심은 **요청을 보낸 객체가 처리 주체를 직접 결정하지 않고, 연결된 Handler들이 순서대로 처리 여부를 판단하도록 하는 것**이다. 확장성은 높일 수 있지만, 연쇄가 길어질수록 실행 흐름을 파악하기 어려워질 수 있으므로 필요한 경우에만 적용해야 한다.
